# Unresolvable Jobs are deferred, then deleted on a clock

**Status:** accepted

A Worker Instance that Claims a due job and cannot load its job class or parameters class no longer deletes the row. It stamps the row with `unresolvable_since`, releases the Claim without moving `perform_at`, skips the job in its own Claim query for five minutes, and looks for other work. Five minutes is the **Resolution Grace**: if the job is still Unresolvable when that window closes, the job is deleted, because no live build ran it while it sat there unclaimed and due. The window is a clock rather than proof — the library never learns which job types a peer can load.

## Context

Several Worker Instances of one application share a single Postgres job table. During a rolling deploy a new instance schedules a job whose class exists only in the new build; an old instance still draining Claims it, fails `Type.GetType`, and — before this decision — deleted the row. Real work was destroyed twice in production (Bugsink COMPLIANCE-6, 2026-08-10 and 2026-09-07); a one-off attestation heal never ran, because the new instance had already finished its boot enqueue path.

An earlier design fixed the loss by deferring such jobs indefinitely with exponential backoff. It traded the data loss for a permanent one: a job class that is genuinely deleted leaves a row nobody can ever run, re-Claimed and re-warned by every instance for the life of the table. That trade was rejected, and this decision replaces it.

## Considered options

- **A clock, not a registry of job types (chosen).** The alternative was for every Worker Instance to publish the job types it can run — a new table or column written at Instance Registration — so the library could delete a row only once no live instance advertised its type. That is evidence rather than a guess, and the existing heartbeat in `job_instances` would have kept it fresh. It was rejected on two grounds. First, the window it protects is not needed: a roll-forward deploy overlaps for minutes, so five minutes separates "a peer is about to run this" from "nobody can" without any instance saying anything. Rolling *back* to a build that lacks a type is explicitly not a case this library protects. Second, the registry cannot be built accurately. `RegisterJob<TJob>()` is not the only way a job becomes runnable — a job registered with plain `services.AddScoped<TJob>()` runs today — so filtering the Claim query by a registry would silently strand jobs that currently work. A wrong registry fails in the same direction as the bug being fixed.
- **Five minutes, not days (chosen).** A time-to-live measured in days keeps orphan rows and their warnings around for days, which is the cost that sank the deferral-only design. Minutes match the thing actually being waited on — a draining instance — rather than an operator's attention span.
- **A dedicated `unresolvable_since` column, not `created_at` (chosen).** `created_at` was the free option: no migration, no new state. It is unsafe. The scheduling upsert's `ON CONFLICT ... DO UPDATE` does not touch `created_at`, so a new instance re-enqueuing a job by name at boot writes onto an existing pending row that keeps its original creation time. A clock read from `created_at` would see "old" and delete precisely the job the deploy was trying to save. The stamp also measures the right thing: how long the job has failed to find a home, not how long ago someone scheduled it.
- **An in-process skip list, not pushing `perform_at` forward (chosen).** Something must stop an instance re-Claiming a job it cannot load in a tight loop. Moving `perform_at` forward is durable and needs no new state, but it delays the instance that *can* run the job by the same step, and — worse — the draining instance sits in a wait loop and would push the job forward again and again, so the capable instance has to win the race on every step of the window. Holding the id in a set in the storage object and excluding it from this instance's own Claim query leaves the row completely untouched: the capable instance sees a due, unclaimed job and takes it at once. The set dies with the process, which is harmless — a restarted instance simply re-Claims and finds the stamp already old.
- **Deletion on the Claim path, not in the periodic sweep (chosen).** `PostgresCleanupService` already ticks every minute and could delete any row whose stamp had aged out, without loading a thing. It would be acting on a stamp another process wrote, with no check that the job is still Unresolvable — so a job that a capable instance merely had not reached within five minutes, behind a backlog, would be destroyed by an instance that knows nothing about it. Deleting on the Claim path costs a little timeliness on a busy queue and buys a re-confirmation at the moment of deletion.
- **Five minutes is a library constant, not a configuration option (chosen).** This is a published NuGet package whose public API is a contract; a knob nobody has asked for is a permanent obligation.

## Consequences

- **The library deletes work on a timer, and that is deliberate.** A Worker Instance able to run a job but too busy to reach it for five minutes will lose that job to an instance that cannot run it. This was accepted knowingly: preserving every job under every schedule was weighed and chosen against.
- **A stale stamp must be cleared, or the fix eats its own tail.** A job stamped by an old instance, run by a new one, and put back by a retry would carry a stamp older than the window and be deleted on the next old-instance Claim with no grace at all. So a Claim that resolves both classes clears any stamp before running, and `TryScheduleRetryAsync` clears it too. A stamp is never acted on without re-confirming that the job is still Unresolvable.
- **The scheduling upsert had to grow, which fixed a separate bug.** Reopening the window on re-scheduling means the `DO UPDATE` list must clear `unresolvable_since` — and while it was being extended, `job_type`, `parameters_type`, `cron_expression`, and `job_group` were added to it. They had been missing, so re-scheduling a job name onto an existing pending row kept the **old** `job_type`: pointing a job name at a different class silently kept running the old class. That is a pre-existing bug this decision closes as a side effect, not a behavior this decision introduces.
- **Deferral is not a failed attempt.** `attempt` is untouched and the deferral never routes through `TryScheduleRetryAsync`, so a job waiting for a peer keeps its full Retry Budget.
- **Warnings now mean something.** Deferring logs at Debug, because deploy overlap is normal and self-correcting; only deletion logs a Warning. The trickle of "the type no longer exists" warnings that motivated this work is gone, replaced by one line per job that genuinely could not be run by anyone.
- **A job that never comes due is never cleaned up.** Resolution Grace opens on Claim, and a job is only Claimed once due, so a row scheduled months ahead whose class is deleted next week rests in the table until it comes due. This is quiet — nothing logs, nothing spins, nothing is lost — and is filed as an Idea rather than solved here.
- **In-memory storage is unaffected**, because it holds live `Type` objects and can never have an Unresolvable Job.
